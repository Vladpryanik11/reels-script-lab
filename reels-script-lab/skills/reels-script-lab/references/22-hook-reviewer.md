# Reels Script Lab — Hook Reviewer v0.2.0

**Назначение:** независимая проверка каждого из трёх хуков и их различий до разработки сценариев.  
**Методология:** `references/21-hook-methodology.md` v0.2.0; первоисточник SMMBOT (https://smmbot.net/blog/formula-uspesnogo-huka-kak-privlec-vnimanie-v-socsetah-220.html).  
**Ограничение:** документ — инструкция. Сам файл и офлайн-валидатор **не являются** независимым запущенным ИИ-ревьювером.

## 1. Что получает Reviewer

- Research Packet v0.2.1 с реальными фактами, статусами, иллюстративными примерами, необходимыми оговорками и источниками;
- исходное пользовательское задание, профиль, цель Reels и длительность;
- полный набор A/B/C с механизмами, текстами, интригами и трёхчастным входом;
- полный каталог разрешённых хуков для строгого профиля — если загружен;
- **без** самооценки Hook Agent в качестве первичного доказательства.

Reviewer отдельно оценивает **каждую** ветку, затем — **межветочную различимость**.

## 2. Блокирующие gates для каждого хука

| ID | Условие | FAIL / NEEDS_EVIDENCE |
|---|---|---|
| G-01 | Хук соответствует теме, аудитории и обещанной развязке | Сценарий не сможет честно выполнить обещание |
| G-02 | Любая эмпирическая/причинная/медицинская претензия имеет разрешённые `claim_id` и оговорки | Необоснованная универсальная причинность или диагноз |
| G-03 | Строгий профиль: только реальный разрешённый каталог с ID и слотами | Каталог отсутствует → `NEEDS_EVIDENCE` |
| G-04 | `viewer_question` и `payoff_contract` содержательны, совместимы и не раскрываются в первой секунде | Кликбейт, пустая интрига, преждевременное раскрытие |
| G-05 | Не нарушены профильная этика, лексика, согласованные ограничения | Стигма, обещание излечения и т.п. |
| G-06 | Исследовательское досье для **production** получило настоящий проверенный `Research Reviewer PASS` | Research PENDING → `BLOCKED_RESEARCH` |
| G-07 | Пример уборки не назван проверяемо доказанным проявлением тревоги | `illustrative_example` превращён в диагноз |
| G-08 | Хук подходит к своей `narrative_route` и будущей точке рехука | Рехук без новой интриги, логика нарушена |

**Стоп-логика:** FAIL нельзя компенсировать баллами. `NEEDS_EVIDENCE` блокирует утверждение, но допускает маркированный просмотр черновика.

## 3. Балльная оценка хука (0–10)

| Критерий | 0 | 1 | 2 |
|---|---|---|---|
| Q-01 — ясность | Не о чем речь | Требует контекста | Смысл понятен сразу |
| Q-02 — конкретность | Общие слова | Частичная сцена | Живое узнаваемое действие |
| Q-03 — интрига/ценность | Нет мотива смотреть | Слабое ожидание | Конкретный вопрос/польза |
| Q-04 — форма | Непроизносимо | Нужен монтаж/сокращение | Естественно и годится для кадра |
| Q-05 — выполнимость обещания | Вводит в заблуждение | С оговорками | Реально раскрывается в сценарии |

Рекомендованный порог: `>=8/10`, нет нулей, все обязательные gates `PASS`. Шкала — редакционная эвристика, не научная метрика вирусности. Длительность 5–6 секунд не штрафовать автоматически.

## 4. Ревью тройки (второй обязательный этап)

- **D-01:** `angle_id` трёх веток различен **содержательно**, а не только по имени;
- **D-02:** `primary_trigger_id` не повторён трижды без обоснования (дополнительные триггеры могут совпадать);
- **D-03:** различаются `viewer_question` и ожидаемая траектория `payoff_contract`;
- **D-04:** предлагаются три разные `narrative_route` и три разные логики развития, а не один сценарий в разной обёртке;
- **D-05:** все три основываются на одном и том же актуальном Research Packet, с разными допустимыми элементами доказательной базы;
- **D-06:** внутри каждого маршрута соблюдён порядок хук → развитие → потенциальная точка рехука → разрешение вопроса. Настоящий Rehook Agent придёт следующим.

Если `D-* FAIL`: вернуть на перепроектирование **одной** слабой ветки, сохранив прошедшие ревью. Не смягчать критерии ради обязательного количества 3.

## 5. Независимость и факты

- Не подтверждать «методология применена» по одному наличию `S-03` в метаданных: привести конкретный фрагмент текста и объяснить действие приёма.
- Проверять каждое потенциально проверяемое утверждение против `allowed_wording`, `source_ids`, `evidence_scope`, даже если `source_claim_ids` у Hook Agent пустые.
- Вопрос тоже может содержать недоказанную предпосылку. Не принимать её автоматически как безопасную.
- Нельзя считать любую уборку избеганием, любое откладывание прокрастинацией, любую прокрастинацию тревогой.
- Если исследований недостаточно — допустим `NEEDS_EVIDENCE`, не придумывать точное число или «гарантированно».

## 6. Цикл исправления

1. Reviewer записывает точный gate/критерий и цитирует фрагмент кандидата.
2. Hook Agent переписывает **только неутверждённую** проблемную ветку.
3. Reviewer проверяет изменённую версию; не наследовать PASS старой версии.
4. Максимум две автоматические итерации, далее — показать пользователю конфликт и варианты.
5. После утверждения делать `approved/locked=true` через контролируемый процесс; меняется хук — заново проверить зависимую структуру, рехук и сценарий этой ветки.

**Запрет ложных успехов:** пример выше демонстрирует структуру; результаты оценок не становятся подтверждёнными от наличия образца отчёта.

## 8. Совместимость с последующими агентами

- Structure Agent обязан развивать именно `narrative_route` выбранной ветки.
- Rehook Agent создаёт новую интригу по `rehook_setup`, не раскрывая до срока `payoff_contract`.
- Script Agent может использовать только разрешённые утверждения из Research Packet и фиксирует ID.
- Humanizer видит `hook_text` только для контекста, правит лишь разрешённые части тела/CTA.
- Comparative Reviewer сравнивает **три завершённых сценария**, а не три отдельных хука; Hook Reviewer не предсказывает просмотры.
